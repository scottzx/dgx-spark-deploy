## 一、 项目背景与硬件底座

### 1. 硬件架构特性
* **设备型号**：NVIDIA DGX Spark
* **芯片规格**：单颗 **NVIDIA GB10 统一内存芯片**
* **物理内存**：128 GB LPDDR5X 统一内存（Unified Memory，CPU 与 GPU 共享统一寻址空间，Linux 宿主机实际可用内存约 **121 GB**）

## 三、 选型大反转：为什么彻底弃用 27B，选定 177B MoE？

在第一期折腾 53 分钟后，原计划“以 27B 作为日常主力，重任务再切 Flash-Next”。但在全链路基准压测与真实场景验证后，我们**彻底推翻了原方案**，直接让 **Qwen3.8-Flash-Next (177B MoE)** 作为唯一常驻主力：

### 核心决策四维度对比

| 评测维度 | Qwen3.8-27B (Dense 稠密) | Qwen3.8-Flash-Next (177B MoE) | 决胜关键点 |
| :--- | :--- | :--- | :--- |
| 🧠 **模型脑容量** | **27B**（参数规模受限） | **176.9B**（顶流旗舰知识储备） | **177B 碾压**：世界知识储备、代码架构、深层逻辑不在同一量级 |
| ⚡ **单步激活算力** | **27B**（每个 Token 全部硬算） | **22.3B**（仅动态激活专家） | **MoE 反直觉红利**：**单步计算负荷甚至低于 27B！** |
| 💾 **128G 显存匹配** | 仅占 28G，闲置 90G 严重浪费 | 占 69G~88G，余量 47G | **完美契合**：彻底榨干 GB10 统一内存硬件红利 |
| 🤖 **Agent 规划能力** | 中规中矩，长逻辑易漂移 | 多轮工具调用稳准狠 | **177B 胜出**：联网搜索多步检索能力大幅提升 |
| 🏃 **生成阅读体验** | ~58 tok/s（速度快但智力受限） | 22 ~ 25 tok/s（每秒 30~40 汉字） | **舒适跟手**：远超人类阅读速度，阅读体验极佳 |

> **结论**：拥有 128G 统一内存工作站跑 27B 是暴殄天物；而 177B MoE 用 177B 的知识底蕴保证顶尖回答质量，又兼具 22B 级别的低算力消耗，无需来回切换双模型，是单机硬件的**天作之合**。

## 四、 生产级常驻 Docker 服务搭建

### 1. 架构与稳定性策略
* **基础镜像**：官方原生 Blackwell/CUDA 13 优化镜像 `ghcr.io/ggml-org/llama.cpp:server-cuda13`。
* **网络与内存**：`--network host --ipc host`，消除虚拟网桥包转发与 IPC 开销。

* **健康检查**：30 秒周期探针 `curl -f http://localhost:8000/health || exit 1`。
* **日志轮转**：`--log-opt max-size=50m --log-opt max-file=3`，防止磁盘写满。
* **接口协议**：标准 OpenAI 兼容协议（监听 `0.0.0.0:8000`）。

## 五、 生产并发与 64K 槽位上下文落地 (方案 B)

### 1. 关键参数设置
在生产常驻启动脚本中显式配置（4 并发槽位 × 每槽 64K 深度）：
```bash
--ctx-size 262144 \
--parallel 4 \
--flash-attn on \
--cache-type-k q8_0 \
--cache-type-v q8_0
```
> **架构机制**：总分配上下文池为 262,144 Token。`llama-server` 自动初始化 `n_slots = 4, n_ctx_slot = 65,536`。支持 4 人或 4 个智能体完全并行交互，每个人独享高达 64K（约 9 万汉字）的超长上下文，彻底解决单槽位排队阻塞。

### 2. 显存与安全性核算 (实测)
* **模型权重**：UD-IQ4_XS 分片加载占用约 **58 GB**。
* **4 槽位 × 64K KV Cache (Q8_0 + FlashAttention)**：初始及运行显存占用约 **69.7 GB**。
* **系统剩余可用物理内存**：**47 GiB 极其充裕的物理缓冲**。
* **Swap 状态**：使用仅 12 KiB（零换页），彻底杜绝 OOM Killer 与磁盘假死风险。

## 六、 实战踩坑血泪史与破局方案

### 坑 1：双实例显存超卖导致系统剧烈换页（Swap Thrashing 假死）
* **现象**：早期尝试拉起两个实例压测，88.5G × 2 瞬间击穿 121GB 物理可用内存，Linux 触发剧烈磁盘 Swap，CPU 和总线被 D-state（不可中断睡眠）占满，SSH 握手无响应，系统假死。
* **破局**：确立**单机单实例常驻**原则。在启动脚本开头执行原子化清理 `docker rm -f`，显存严格锁死在 75GB 内部，预留 40GB+ 安全物理空间。

### 坑 2：并发槽位的除法陷阱（`n_ctx_slot = ctx_size / parallel`）
* **现象**：初次压测时配置了 `--parallel 16 --ctx-size 32768`，结果发现请求输入超过 2,048 Token 时直接报错被强制截断。
* **破局**：厘清 `llama-server` 的内存分配模型：单个 Slot 的上下文容量为 `ctx_size ÷ parallel`。对于长文档业务，必须配置 `--ctx-size 131072 --parallel 1`，将完整的 128K 深度独享分配给工作槽位。

### 坑 3：长文本首字延迟（TTFT）过长导致客户端超时断连
* **现象**：用户发送 1.35 万 Token 的长文档请求，默认微批次配置下预处理耗时 68 秒才出首字。常用客户端（Cherry Studio、Chatbox 等）默认请求超时为 30s/60s，等待 60s 后主动断开报“网络连接失败”，且由于单槽位被占用 95 秒，后续请求全部排队卡死。
* **破局**：
  1. 服务端实施微批次翻倍调优（见第七节），Prefill 速度提升 3.6 倍，首字降至 18 秒内。
  2. 客户端高级设置中将 Request Timeout 调整为 180s ~ 300s。

### 坑 4：多模态 mmproj 挂载后的 Cache 机制告警
* **现象**：加载 `mmproj-BF16.gguf` 后，后台提示 `cache_reuse is not supported by multimodal, it will be disabled`。
* **破局**：该提示仅针对动态 KV-shifting 机制；纯文本对话基于 **LCP（最长公共前缀）的原生 Prompt Cache 依然完美生效**，在多轮对话中依然能实现 90%+ 的缓存命中。

## 七、 首字延迟 (TTFT) 极速调优秘籍

### 1. 核心破局点：计算微批次 (Micro-batch) 压榨
MoE 架构由于稀疏路由，默认参数 `--ubatch-size 512` 会导致每次分摊到每个 Expert 专家的 Token 极少，导致矩阵乘法退化为访存受限，NVIDIA GB10 的 Tensor Core 算力严重不饱和。

### 2. 调优参数组合
```bash
--batch-size 4096 \
--ubatch-size 2048 \
--cache-reuse 256
```

### 3. 实测性能对比数据

| 核心指标 | 优化前默认配置 | 优化后实测数据 | 提升幅度 |
| :--- | :--- | :--- | :--- |
| **长文本预处理吞吐 (Prefill)** | `197.13 tok/s` | **`713.39 tok/s`** | ⚡ **提速 262%（3.62 倍）** |
| **1.35 万 Token 首字延迟** | **68.2 秒**（超时断连） | **~18.8 秒** | ⏱️ **破除客户端 30s/60s 超时** |
| **3,652 Token 首字耗时** | ~18.5 秒 | **5.11 秒** | ⏱️ **5 秒即可看到首字** |
| **多轮对话 / 追问 (Cache 命中)** | 需全量重算 | **0.56 秒**（复用 3648 Token） | 🚀 **近乎瞬间毫秒级出字** |
| **持续输出吐字速度** | ~22.0 tok/s | **21.7 ~ 24.5 tok/s** | 🏃 **稳定 30~40 汉字/秒** |

## 八、 真实业务多轮 Agent 检索实测验证

用户通过客户端执行真实 **「搜索今日新闻」** 联网 Agent 检索全流程：
1. **多步工具规划**：模型先后执行 6 轮搜索关键词生成，每次 1~3 秒迅速返回。
2. **第一次汇总成文**：累计注入上下文 9,124 Token，首字 3.58 秒打出，生成 879 字新闻初稿，生成速度 22.86 tok/s。
3. **第二次深度长文生成**：
   * **总上下文规模**：膨胀至 **22,368 Token（约 3 万汉字）**。
   * **前缀缓存命中**：系统通过 LCP 自动复用前序 **20,517 Token** 缓存！
   * **首字耗时**：面对 2.2 万 Token，仅需预计算新增部分，**10.37 秒** 即开始出字（若全量重算需 110 秒以上）。
   * **长文生成**：稳定以 21.73 tok/s 吐出 **1,183 字** 深度长文，全流程 0 截断、0 报错，显存平稳保持在 **69.0 GB**。

## 十、 500 会话透明持久化与 NVMe FIFO 智能调度中间件

### 1. 架构设计与实现原理
针对“多任务切换频繁、会话被踢出后重算耗时”的痛点，构建了双层透明分级调度架构：
* **底层推理引擎**：`llama-server`（Docker 容器）监听内部 `8001` 端口，开启 `--slot-save-path /slots`，与宿主机 NVMe SSD（`/home/admin/slot_cache`）打通。
* **前置透明代理**：`session_fifo_proxy.py` 监听标准客户端 `8000` 端口，无需客户端修改任何配置。
  1. **特征提取**：自动提取会话首问指纹（Session Hash）或客户端显式 Header；
  2. **毫秒级恢复 (Restore)**：当发现会话在显存中已被淘汰但 SSD 中有快照时，先以 **0.9 ~ 3.0 毫秒** 速度瞬间还原槽位；
  3. **异步存盘 (Save)**：生成完成后，异步以 **1.4 ~ 5.7 毫秒** 速度将最新状态 Dump 到 NVMe SSD；
  4. **严格 FIFO 淘汰**：维护 `fifo_index.json`，队列留存上限扩容至 **500 个历史会话快照**。超出 500 个自动删除最旧快照文件，保证磁盘空间永远可控（500 会话通常仅占 1.5GB ~ 5GB NVMe 空间）。

### 2. 实测运行指标
* **NVMe 读盘恢复耗时**：**0.9 ~ 2.5 ms**（相比从头 Prefill 重新推理 40 秒，提速数万倍！）；
* **NVMe 异步存盘耗时**：**1.4 ~ 5.7 ms**；
* **单次快照体积**：约几百 KB 至几 MB（多轮 1.6K tokens 约 2.7MB）；
* **首字延迟收益**：跨天/跨多任务切回历史大文档，首字延迟直接维持在 **0.3 ~ 0.5 秒** 瞬时输出；
* **容量规格**：**4 槽位显存并行计算 + 500 会话 NVMe SSD 持久化轮替**。
